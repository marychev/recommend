# Отчёт: Pipeline Benchmark Kafka→ClickHouse

**Дата:** 22-23.03.2026
**Среда:** Docker, 5.8GB RAM, 1 worker uvicorn
**Инструмент:** k6 (load-test-post-quick, measure-insert-lag, spike-test)

---

## Задача

Выбрать оптимальный способ доставки данных из Kafka в ClickHouse для рекомендательной системы музыкальных треков. Три варианта, одинаковые тесты, одна среда.

## Что сравнивали

| Решение | Суть | Кто предлагает |
|---------|------|----------------|
| **A. Python Consumer** | aiokafka читает из Kafka, батчит в буфер, HTTP INSERT в CH. Наш код, полный контроль | Текущая реализация проекта |
| **B. Kafka Connect Sink** | JVM-процесс с ClickHouse Sink Connector. Декларативная конфигурация, без кода | Confluent / ClickHouse Inc. Стандартный подход в Kafka-экосистеме |
| **C. Kafka Table Engine** | ClickHouse сам читает из Kafka через встроенный движок. SQL-only, ноль внешнего кода | ClickHouse Inc. Рекомендуется в документации CH для простых сценариев |

## Решение

**Оставляем Python Consumer (A)** как основное решение.

Причины:
1. **Redis side-effects** — единственное решение с обновлением метрик/аналитики при событиях
2. **Полный контроль** — кастомная логика обработки, fallback, батчинг

**Решение C (Engine)** — лидер по spike-производительности (60ms avg, 6698 запросов). Подходит для сценариев без side-effects.

**Решение B (Connect)** — enterprise-вариант с exactly-once гарантиями. Подходит при необходимости JVM-экосистемы.

## Ключевой урок

Оба бага (B и C) имели **корневую причину** — несовместимость формата datetime:
- **B:** `.isoformat()` → `.strftime('%Y-%m-%d %H:%M:%S')` в producer'е
- **C:** `parseDateTimeBestEffort()` → `parseDateTime(field, '%Y-%m-%d %H:%M:%S')` в MV

Стандартизация через `format_datetime_ch()` и `parseDateTime()` исправила оба решения.
