# Отчёт: Pipeline Benchmark Kafka→ClickHouse

**Дата:** 22-23.03.2026
**Среда:** Docker, 5.8GB RAM, 1 worker uvicorn
**Инструмент:** k6 (load-test-post-quick, measure-insert-lag, spike-test)

---

## Задача

Выбрать оптимальный способ доставки данных из Kafka в ClickHouse для рекомендательной системы музыкальных треков. Три варианта, одинаковые тесты, одна среда.

## Что сравнивали

| Решение | Суть | Кто предлагает |
|---------|------|----------------|
| **A. Python Consumer** | aiokafka читает из Kafka, батчит в буфер, HTTP INSERT в CH. Наш код, полный контроль | Текущая реализация проекта |
| **B. Kafka Connect Sink** | JVM-процесс с ClickHouse Sink Connector. Декларативная конфигурация, без кода | Confluent / ClickHouse Inc. Стандартный подход в Kafka-экосистеме |
| **C. Kafka Table Engine** | ClickHouse сам читает из Kafka через встроенный движок. SQL-only, ноль внешнего кода | ClickHouse Inc. Рекомендуется в документации CH для простых сценариев |

## Результаты

### Нормальная нагрузка (10 VUs, 1 мин)

| | A: Python | B: Connect (до фикса) | B: Connect (после фикса) | C: Engine |
|---|---|---|---|---|
| RPS | 90 | 58 | **101** | 96 |
| Events avg | 191ms | 290ms | **163ms** | 179ms |
| Recommendations avg | 180ms | 334ms | **144ms** | 184ms |
| Ошибки | 0% | 0% | 0% | 0% |

После фикса timestamp (23.03) решение B стало лидером по RPS. До фикса Connect тратил ресурсы на обработку ошибок вставки, что снижало общую производительность.

### Доставка данных (insert lag, 50 запросов)

| | A: Python | B: Connect (до фикса) | B: Connect (после фикса) | C: Engine |
|---|---|---|---|---|
| Avg lag | -453ms | не работает | **-489ms** | -485ms |
| Доставлено | 100% | 0% | **100%** | 100% |

Отрицательный лаг = данные появляются в CH быстрее, чем API отвечает клиенту (батч уже готов).

**Фикс (23.03):** Баг был в сериализации producer'а — `.isoformat()` генерировал `"2026-03-23T14:30:45.123456"` (ISO 8601 с `T` и микросекундами), несовместимый с ClickHouse `DateTime`. Заменили на `.strftime('%Y-%m-%d %H:%M:%S')` → `"2026-03-23 14:30:45"`. После фикса — 100% доставка, лаг на уровне других решений.

### Пиковая нагрузка (spike 50 VUs, ramp-up 30с)

| | A: Python | B: Connect (до фикса) | B: Connect (после фикса) | C: Engine |
|---|---|---|---|---|
| Запросов | 1241 | 568 | **3857** | 429 |
| Avg время ответа | 1.8с | 4.3с | **0.26с** | 78с |
| p95 | 10.8с | 26.3с | **1.0с** | 1263с |
| Ошибки | 0% | 0% | **0%** | crash + timeouts |
| Длительность теста | 1.5 мин | 1.5 мин | 1.8 мин | **21 мин** (завис) |

**A** — деградация есть, но без потерь.
**B (до фикса)** — вдвое медленнее, Connect тратил ресурсы на обработку ошибок вставки.
**B (после фикса)** — лучший результат: 3857 запросов, avg 257ms. Connect работает корректно, ClickHouse не перегружается ошибками.
**C** — ClickHouse упал (OOM). CH одновременно читает из Kafka + обрабатывает API-запросы → RAM 60% → crash.

## Решение

**Оставляем Python Consumer (A)** как основное решение.

Причины:
1. **Redis side-effects** — обновление метрик/аналитики при событиях (Connect этого не умеет)
2. **Нет JVM-зависимости** — проще деплой, меньше RAM (+836MB за Connect)
3. **Полный контроль** — кастомная логика обработки, fallback, батчинг

**Решение B (Connect)** — после фикса timestamp стало полностью рабочим и показало лучшие результаты по throughput (101 RPS) и spike-устойчивости (257ms avg vs 1822ms у A). Подходит как альтернатива для сценариев без Redis side-effects.

## Что делать дальше

Bottleneck проекта — не пайплайн, а **ClickHouse** (CPU 311%, RAM 52% при spike). Направления:

1. **Увеличить ресурсы CH** — поднять RAM лимит, выделить CPU
2. **Масштабировать API** — добавить uvicorn workers (сейчас 1)
3. **Оптимизировать запросы** — ревизия MV, индексов, тяжёлых SELECT
