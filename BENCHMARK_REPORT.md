# Отчёт: Pipeline Benchmark Kafka→ClickHouse

**Дата:** 22.03.2026
**Среда:** Docker, 5.8GB RAM, 1 worker uvicorn
**Инструмент:** k6 (load-test-post-quick, measure-insert-lag, spike-test)

---

## Задача

Выбрать оптимальный способ доставки данных из Kafka в ClickHouse для рекомендательной системы музыкальных треков. Три варианта, одинаковые тесты, одна среда.

## Что сравнивали

| Решение | Суть | Кто предлагает |
|---------|------|----------------|
| **A. Python Consumer** | aiokafka читает из Kafka, батчит в буфер, HTTP INSERT в CH. Наш код, полный контроль | Текущая реализация проекта |
| **B. Kafka Connect Sink** | JVM-процесс с ClickHouse Sink Connector. Декларативная конфигурация, без кода | Confluent / ClickHouse Inc. Стандартный подход в Kafka-экосистеме |
| **C. Kafka Table Engine** | ClickHouse сам читает из Kafka через встроенный движок. SQL-only, ноль внешнего кода | ClickHouse Inc. Рекомендуется в документации CH для простых сценариев |

## Результаты

### Нормальная нагрузка (10 VUs, 1 мин)

| | A: Python | B: Connect | C: Engine |
|---|---|---|---|
| RPS | 90 | 58 | **96** |
| Events avg | 191ms | 290ms | **179ms** |
| Recommendations avg | 180ms | 334ms | **184ms** |
| Ошибки | 0% | 0% | 0% |

При спокойной нагрузке решение C чуть быстрее — ClickHouse читает данные напрямую, без промежуточного процесса. Решение B заметно медленнее из-за JVM overhead.

### Доставка данных (insert lag, 50 запросов)

| | A: Python | B: Connect | C: Engine |
|---|---|---|---|
| Avg lag | -453ms | **не работает** | **-485ms** |
| Доставлено | 100% | 0% | 100% |

Отрицательный лаг = данные появляются в CH быстрее, чем API отвечает клиенту (батч уже готов).

**Connect провалился** — ошибка парсинга `created_at` (формат timestamp несовместим с ClickHouse). Данные молча отбрасываются из-за `errors.tolerance=all`. Это не баг нагрузки, а баг конфигурации — требует доработки конвертеров.

### Пиковая нагрузка (spike 50 VUs, ramp-up 30с)

| | A: Python | B: Connect | C: Engine |
|---|---|---|---|
| Запросов | 1241 | 568 | 429 |
| Avg время ответа | **1.8с** | 4.3с | 78с |
| p95 | **10.8с** | 26.3с | 1263с |
| Ошибки | **0%** | 0% | crash + timeouts |
| Длительность теста | 1.5 мин | 1.5 мин | **21 мин** (завис) |

**A** — деградация есть, но без потерь.
**B** — вдвое медленнее, но устоял.
**C** — ClickHouse упал (OOM). CH одновременно читает из Kafka + обрабатывает API-запросы → RAM 60% → crash. Тест завис на 21 минуту с таймаутами.

### Ресурсы при пиковой нагрузке

| | A: Python | B: Connect | C: Engine |
|---|---|---|---|
| CH CPU пик | 311% | 461% | 343% → crash |
| CH RAM пик | 3.0GB (52%) | 3.3GB (57%) | 3.5GB (60%) → OOM |
| Доп. процессы | — | Connect 570MB | — |
| Итого RAM | 3.7GB | 4.4GB | 4.1GB → crash |

ClickHouse — bottleneck во всех трёх решениях.

## Сводка

| Критерий | A: Python | B: Connect | C: Engine |
|----------|-----------|------------|-----------|
| RPS (норм.) | 90 | 58 | 96 |
| Доставка данных | 100% | 0% (баг) | 100% (норм.) / потери (spike) |
| Устойчивость к spike | стабильно | медленно | crash |
| Redis side-effects | да | нет | нет |
| Доп. RAM | 0 | +570MB | 0 |
| Сложность кода | Python | конфигурация | SQL |
| Production-ready | **да** | нет | опасно |

## Решение

**Оставляем Python Consumer (A).**

Единственное решение, которое:
1. Не теряет данные ни при какой нагрузке
2. Поддерживает Redis side-effects (обновление метрик/аналитики при событиях)
3. Не требует дополнительных процессов и памяти
4. Выдерживает spike без crash'ей

## Что делать дальше

Bottleneck проекта — не пайплайн, а **ClickHouse** (CPU 311%, RAM 52% при spike). Направления:

1. **Увеличить ресурсы CH** — поднять RAM лимит, выделить CPU
2. **Масштабировать API** — добавить uvicorn workers (сейчас 1)
3. **Оптимизировать запросы** — ревизия MV, индексов, тяжёлых SELECT
