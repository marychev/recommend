# 📝 Нагрузочное тестирование POST запросов

Руководство по тестированию POST эндпоинтов API с помощью k6.

## 🎯 Что тестируется

Тест проверяет производительность следующих POST эндпоинтов:

1. **POST /api/v1/users** - создание пользователя
2. **POST /api/v1/tracks** - создание трека
3. **POST /api/v1/events** - создание события взаимодействия
4. **POST /api/v1/recommendations** - получение рекомендаций

## 🚀 Быстрый старт

### Базовый запуск

```bash
# Стандартный тест (50 VUs, 5 минут)
make load-test-post

# Быстрый тест (10 VUs, 1 минута)
make load-test-post-quick
```

### Настройка нагрузки

```bash
# Кастомное количество пользователей и длительность
make load-test-post VUS=100 DURATION=10m

# Или напрямую через k6
k6 run load_tests/k6_post_load_test.js --vus 100 --duration 10m
```

## 📊 Что измеряется

### Метрики производительности

- **Время ответа** (avg, p95, p99, max) для каждого endpoint
- **Процент успешных запросов** (rate > 95%)
- **Количество ошибок** по каждому endpoint
- **RPS** (запросов в секунду)
- **Максимальное количество параллельных пользователей**

### Пороговые значения (thresholds)

- `post_create_user_duration`: p95 < 3000ms, p99 < 5000ms
- `post_create_track_duration`: p95 < 3000ms, p99 < 5000ms
- `post_create_event_duration`: p95 < 2000ms, p99 < 4000ms
- `post_get_recommendations_duration`: p95 < 10000ms, p99 < 20000ms
- `http_req_failed`: rate < 5%
- Успешность каждого endpoint: rate > 90-95%

  "genre": "Rock",

  "user_id": 1001,

  "listen_duration_seconds": 180

```json
{

  "top_n": 10,
  "exclude_listened": true,
  "include_performance_metrics": false
}
```

## 📈 Профиль нагрузки

По умолчанию тест использует следующий профиль:

```
0-30s:   20% VUs  (разогрев)
30-90s:  50% VUs  (рост)
90s-5m:  100% VUs (стабильная нагрузка)
5-6m:    150% VUs (пиковая нагрузка)
6-6.5m:  0 VUs    (завершение)
```

## 🎯 Когда использовать

### ✅ Рекомендуется запускать:

- После изменений в POST эндпоинтах
- Перед релизом новой версии
- При планировании масштабирования
- Для определения пропускной способности записи данных
- При оптимизации производительности создания ресурсов

### ⚠️ Важные замечания:

1. **Тест создает реальные данные** в БД
   - Пользователи и треки будут добавлены в ClickHouse
   - События будут отправлены в Kafka
   - Рекомендации будут кэшироваться в Redis

2. **Используйте тестовую БД** для нагрузочных тестов
   - Не запускайте на production без подготовки
   - Убедитесь, что есть достаточно места в БД

3. **Мониторинг ресурсов**
   - Следите за использованием CPU/RAM
   - Проверяйте логи ClickHouse и Kafka
   - Мониторьте Redis

## 🔍 Анализ результатов

### ✅ Хорошие результаты

- p95 < 2000ms для создания ресурсов
- p95 < 5000ms для рекомендаций
- Процент ошибок < 5%
- Успешность > 95%

### ⚠️ Требует внимания

- p95 > 3000ms для создания ресурсов
- p95 > 10000ms для рекомендаций
- Процент ошибок > 5%
- Деградация производительности со временем

### ❌ Критично

- p95 > 5000ms для создания ресурсов
- p95 > 20000ms для рекомендаций
- Процент ошибок > 10%
- Система не выдерживает нагрузку

## 🛠️ Troubleshooting

### Проблема: Высокий процент ошибок

```bash
# Проверьте логи API
make logs-errors

# Проверьте статус сервисов
make ps

# Проверьте подключение к БД
docker-compose logs clickhouse | tail -50
```

### Проблема: Медленные ответы

```bash
# Проверьте индексы в БД
make db-indexes

# Проверьте статистику БД
make db-stats

# Проверьте ресурсы Docker
docker stats
```

### Проблема: Недостаточно данных

```bash
# Сгенерируйте тестовые данные
make load-test-data-generate

# Проверьте количество записей
make db-stats
```
