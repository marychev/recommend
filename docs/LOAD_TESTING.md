## Введение

Нагрузочное тестирование позволяет:

- ✅ Проверить производительность API под нагрузкой
- ✅ Выявить узкие места в системе
- ✅ Определить максимальную пропускную способность
- ✅ Проверить поведение при пиковых нагрузках
- ✅ Обнаружить утечки памяти и деградацию производительности

## Быстрый старт

Полное руководство: [load_tests/QUICKSTART.md](../load_tests/QUICKSTART.md)

### Минимальные шаги:

```bash
# 1. Установить k6
brew install k6  # macOS

# 2. Установить зависимости
pip install -r requirements.txt

# 3. Запустить сервисы
make up
make db-init

# 4. Сгенерировать данные
make load-test-data-generate

# 5. Запустить тест
make load-test-quick
```

## Архитектура тестирования

### Структура директории `load_tests/`

```
load_tests/
├── generate_test_data.py       # Генерация 1M записей с Faker
├── k6_basic_load_test.js       # Базовый нагрузочный тест
├── k6_spike_test.js            # Тест пиковой нагрузки
├── k6_stress_test.js           # Стресс-тест
├── k6_soak_test.js             # Тест на выносливость
├── quick_test.js               # Быстрая проверка API
├── run_all_tests.sh            # Скрипт для запуска всех тестов
├── README.md                   # Подробная документация
├── QUICKSTART.md               # Краткое руководство
└── .gitignore                  # Игнорируемые файлы
```

### Компоненты

1. **Генератор данных** (`generate_test_data.py`)
   - Использует библиотеку Faker
   - Создает 100k пользователей
   - Создает 50k треков
   - Создает 850k взаимодействий

2. **k6 скрипты**
   - Написаны на JavaScript
   - Используют k6 HTTP модуль
   - Определяют сценарии нагрузки
   - Собирают метрики

3. **Makefile команды**
   - Упрощают запуск тестов
   - Автоматизируют процесс
   - Обеспечивают консистентность

## Типы тестов

### 1. Quick Test (30 секунд)

**Назначение:** Быстрая проверка готовности API к тестированию

```bash
make load-test-quick
```

**Параметры:**
- VUs: 5
- Длительность: 30s
- Эндпоинты: /, /users, /tracks, /recommendations

### 2. Basic Load Test (~15 минут)

**Назначение:** Базовый нагрузочный тест с реалистичными сценариями

```bash
make load-test-basic
```

**Сценарий нагрузки:**
```
50 VUs  ────────┐
                │
100 VUs         ├─────────────┐
                              │
200 VUs (пик)                 ├────┐
                                   │
50 VUs                             └──────┐
                                          │
0 VUs                                     └───
```

**Тестируемые эндпоинты:**
- GET `/api/v1/users` (30%)
- GET `/api/v1/tracks` (30%)
- GET `/api/v1/recommendations/{user_id}` (40%)

**Пороги успеха:**
- p(95) < 2000ms
- p(99) < 5000ms
- Ошибки < 5%

### 3. Spike Test (~3 минуты)

**Назначение:** Проверка поведения при резком росте трафика

```bash
make load-test-spike
```

**Сценарий:**
```
10 VUs  ───┐
           │
500 VUs    └─┐  (резкий скачок за 10s)
             │
             ├────────  (удержание 1 минуту)
             │
10 VUs       └──┐  (резкое падение)
                └────
```

**Проверяет:**
- Устойчивость к резким нагрузкам
- Восстановление после пика
- Поведение автомасштабирования

### 4. Stress Test (~30 минут)

**Назначение:** Определение точки отказа системы

```bash
make load-test-stress
```

**Сценарий:**
```
50 VUs   ────┐
             │
100 VUs      ├─────┐
                   │
200 VUs            ├─────┐
                         │
300 VUs                  ├─────┐
                               │
400 VUs                        ├─────┐
                                     │
500 VUs                              ├─────
                                           
0 VUs                                      └──
```

**Фокус на тяжелых запросах:**
- Рекомендации (50%)
- Статистика (25%)
- Большие списки (25%)

### 5. Soak Test (~70 минут)

**Назначение:** Выявление утечек памяти и деградации

```bash
make load-test-soak
```

**Сценарий:**
```
50 VUs  ────┐
            │
            ├────────────────────────────────  (1 час)
            │
0 VUs       └────
```

**Проверяет:**
- Стабильность в течение времени
- Утечки памяти
- Деградацию производительности
- Накопление ошибок

## Метрики и анализ

### Основные метрики k6

| Метрика | Описание | Хорошее значение |
|---------|----------|------------------|
| `http_req_duration` | Время ответа | p(95) < 2000ms |
| `http_req_failed` | % неудачных запросов | < 5% |
| `http_reqs` | Запросов в секунду | Зависит от нагрузки |
| `vus` | Виртуальных пользователей | По сценарию |
| `iteration_duration` | Время итерации | p(95) < 10000ms |

### Кастомные метрики

- `users_response_time` - время ответа для users эндпоинтов
- `tracks_response_time` - время ответа для tracks эндпоинтов
- `recommendations_response_time` - время ответа для recommendations
- `errors` - счетчик ошибок

### Интерпретация результатов

#### ✅ Отличная производительность

```
http_req_duration..............: avg=250ms   p(95)=800ms   p(99)=1500ms
http_req_failed................: 0.50%
```

#### ⚠️ Приемлемая производительность

```
http_req_duration..............: avg=800ms   p(95)=1800ms  p(99)=4500ms
http_req_failed................: 4.50%
```

#### ❌ Проблемная производительность

```
http_req_duration..............: avg=3000ms  p(95)=8000ms  p(99)=15000ms
http_req_failed................: 15.00%
```

### Анализ результатов

**Признаки проблем:**

1. **Высокое время ответа**
   - Оптимизируйте запросы к БД
   - Добавьте индексы
   - Увеличьте кэширование

2. **Высокий процент ошибок**
   - Проверьте логи: `make logs-errors`
   - Увеличьте connection pools
   - Проверьте ресурсы БД

3. **Растущее время ответа**
   - Возможная утечка памяти
   - Проблемы с connection pools
   - Деградация производительности БД

4. **Падение RPS при росте VUs**
   - Достигнут предел системы
   - Требуется масштабирование
   - Узкое место в архитектуре

## Best Practices

### Подготовка к тестированию

1. **Инфраструктура**
   - Выделите достаточные ресурсы (CPU, RAM)
   - Убедитесь в стабильности сети
   - Закройте другие приложения

2. **Данные**
   - Сгенерируйте реалистичные данные
   - Используйте достаточный объем (1M записей)
   - Проверьте распределение данных

3. **Мониторинг**
   - Настройте логирование
   - Подготовьте инструменты мониторинга
   - Отслеживайте метрики системы

### Последовательность запуска

```bash
# 1. Quick test - проверка готовности
make load-test-quick

# 2. Basic test - базовая проверка
make load-test-basic

# 3. Spike test - пиковые нагрузки
make load-test-spike

# 4. Stress test - поиск пределов
make load-test-stress

# 5. Soak test - долгосрочная стабильность (опционально)
make load-test-soak
```

### Оптимизация производительности

**На основе результатов тестов:**

1. **ClickHouse**
   ```sql
   -- Добавьте индексы
   ALTER TABLE users ADD INDEX idx_user_id user_id TYPE minmax;
   
   -- Оптимизируйте таблицы
   OPTIMIZE TABLE users;
   ```

2. **Redis кэширование**
   - Увеличьте TTL для рекомендаций
   - Кэшируйте популярные запросы
   - Используйте prefetching

3. **API**
   - Увеличьте worker processes
   - Настройте connection pooling
   - Используйте async/await

4. **Инфраструктура**
   - Горизонтальное масштабирование
   - Load balancing
   - CDN для статики

### Troubleshooting

#### Проблема: Тесты не запускаются

```bash
# Проверьте установку k6
k6 version

# Проверьте API
curl http://localhost:8000

# Проверьте сервисы
make ps
```

#### Проблема: Много ошибок 500

```bash
# Проверьте логи
make logs-errors

# Проверьте БД
make db-stats

# Перезапустите сервисы
make restart
```

#### Проблема: Низкая производительность

```bash
# Проверьте ресурсы
docker stats

# Проверьте кэш
docker-compose logs redis | grep -i error

# Проверьте ClickHouse
docker-compose logs clickhouse | grep -i error
```
