## 🔧 ТЕХНИЧЕСКАЯ РЕАЛИЗАЦИЯ

### 1. Конфигурируемый TTL

**Добавлена настройка в `app/config.py`:**
```python
class Settings(BaseSettings):
    # Cache settings
    recommendations_cache_ttl: int = 3600  # 1 час по умолчанию
```

**Динамическое получение TTL в `app/services/cache.py`:**
```python
def get_cache_ttl() -> int:
    """Получить TTL для кэша рекомендаций из конфигурации"""
    return settings.recommendations_cache_ttl
```

### 2. API для управления TTL

**Новые эндпоинты в `app/routers/cache_debug.py`:**

- `POST /api/v1/debug/cache/set-ttl/{hours}` - установить TTL (1-24 часа)
- `GET /api/v1/debug/cache/current-ttl` - получить текущий TTL

**Пример использования:**
```bash
# Установить TTL 4 часа
curl -X POST http://localhost:8000/api/v1/debug/cache/set-ttl/4

# Проверить текущий TTL
curl http://localhost:8000/api/v1/debug/cache/current-ttl
```

### 3. Обновленная логика кэширования

**Модифицированная функция `set_cached_recommendations`:**
```python
async def set_cached_recommendations(
    user_id: int,
    top_n: int,
    exclude_listened: bool,
    recommendations: Dict[str, Any],
    ttl: int = None,  # Если None, используется из настроек
) -> bool:
    # Используем TTL из настроек, если не передан явно
    if ttl is None:
        ttl = get_cache_ttl()
```

## 📊 ТЕОРЕТИЧЕСКИЙ АНАЛИЗ ВЛИЯНИЯ TTL

### Математическая модель hit rate:

**Hit Rate = (Запросы в пределах TTL) / (Общее количество запросов)**

| TTL | Вероятность повторного запроса | Ожидаемый Hit Rate | Обоснование |
|-----|-------------------------------|-------------------|-------------|
| **1 час** | 60% | 60% | Baseline (текущий результат) |
| **2 часа** | 70-75% | 70-75% | Больше времени для повторных запросов |
| **4 часа** | 75-80% | 75-80% | Максимальное время без потери актуальности |
| **8+ часов** | 80%+ | 80%+ | Риск устаревания рекомендаций |

### Факторы, влияющие на эффективность:

1. **Паттерны пользователей:**
   - Активные пользователи: запросы каждые 30-60 минут
   - Обычные пользователи: запросы каждые 2-4 часа
   - Редкие пользователи: запросы раз в день

2. **Селективная инвалидация:**
   - LIKE/DISLIKE: инвалидирует кэш независимо от TTL
   - PLAY/SKIP: не влияют на кэш
   - Частота значимых событий: ~10-20% от всех событий

### Экономический эффект:

**При hit rate 75%:**
- **75% запросов** обрабатываются за 1-7ms (из кэша)
- **25% запросов** обрабатываются за 300-800ms (из ClickHouse)
- **Снижение нагрузки на ClickHouse в 4 раза** по сравнению с исходным состоянием
- **Улучшение пользовательского опыта** для 75% запросов

## ⚖️ АНАЛИЗ РИСКОВ И КОМПРОМИССОВ

### Потенциальные риски:

1. **Устаревание рекомендаций:**
   - **Риск:** При TTL 4+ часа рекомендации могут стать менее актуальными
   - **Митигация:** Селективная инвалидация при значимых событиях (LIKE/DISLIKE)

2. **Увеличение потребления памяти Redis:**
   - **Риск:** Больше данных хранится дольше
   - **Оценка:** Незначительный рост (~20-30%)

3. **Сложность отладки:**
   - **Риск:** Дольше живущий кэш сложнее отлаживать
   - **Митигация:** Детальное логирование и API для управления

### Компромиссы:

| Аспект | Плюсы | Минусы |
|--------|-------|--------|
| **TTL 2 часа** | Умеренное улучшение hit rate, низкий риск | Не максимальная производительность |
| **TTL 4 часа** | Максимальный hit rate, отличная производительность | Небольшой риск устаревания |
| **TTL 8+ часов** | Очень высокий hit rate | Высокий риск устаревания рекомендаций |
